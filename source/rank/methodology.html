算法与数据口径

这份榜单的每个名次都应该能被复算、被质疑、被回溯。下面把口径全部摊开。

一、这个榜是什么，不是什么

它统计的是 在 GitHub 上有公开可核验仓库、且属于某个 AI Agent 平台插件生态的项目，按当日公开指标排序。它不是官方下载量榜，也不代表插件的实际使用人数或质量评审。

数据分两层：榜单页（本页下述评分口径，总榜与各分榜各取前 100）和 官方市场目录页（各平台本地市场清单的全量条目，不做分数排序）。

最重要的局限：Codex、WorkBuddy 等平台的官方市场里存在大量没有公开 GitHub 仓库的闭源技能、连接器与专家包。它们不参与总榜分数排序（否则「中性缺失」会把零数据实体抬进 Top 100），但会在官方市场目录页完整列出。这是数据可得性的边界，不是遗漏，也不会用估算值补齐。

二、评分公式

Score = 100 × Σ( wᵢ · norm(xᵢ) ) / Σ( wᵢ 可用 )

norm 用当日全样本分位（并列取平均名次），而不是除以最大值，避免头部仓库碾压长尾；stars / forks / 下载量这类长尾指标先取 log1p。四个维度：

维度原始权重构成数据来源
热度 P0.40stars 0.60 + forks 0.30 + npm 周下载 0.10（子项按可用性重归一）GitHub API / npm downloads API
活跃 A0.25exp(−Δt / 90)，Δt 为最近 push 距今天数GitHub pushed_at
势能 M0.25与 ≤7 天前历史快照比较的 stars 增量分位本站 data/history/ 快照
质量 Q0.10license 0.25、描述完整度 0.20、主页 0.15、topics 0.15、wiki/pages 0.15、语言 0.10GitHub 仓库元数据

三、缺失数据怎么处理

  • 不填 0，不估算。某个维度整体不可用时（例如首日还没有历史快照 → 势能 M 缺失），该维度权重从分母剔除，剩余维度重新归一，并在详情页该维度标 n/a 权重已重归一。
  • 首日有效权重为 P 0.5333 / A 0.3333 / Q 0.1333；从第二天起恢复为 0.40 / 0.25 / 0.25 / 0.10。
  • npm 下载量只在仓库主页明确指向 npmjs.com/package/… 时才取，不靠仓库名猜包名；取不到就标 n/a。
  • 详情页的「数据置信度」按 license / 主页 / 描述长度 / topics 数 / 下载量五项命中数计算，分为高（≥4）、中（≥2）、低。

四、去重与平台归属

  • 唯一实体 canonical = owner/repo（小写）。同一个仓库被多个平台 topic 命中时合并为一个实体，platforms 保留多值 —— 总榜不会被同一插件刷屏。
  • 平台归属 = 采集 query 来源 ∪ 仓库 topics 交叉命中。例如同时打了 claude-code 与 dsh-plugin 的仓库，会同时出现在两个分榜，但在总榜里只算一个。
  • 总榜与各平台分榜各自取前 100。某平台样本不足 100 时如实显示实际条数并标注，不降低标准凑数。

五、准入与反作弊

  • 剔除：已归档仓库、fork 仓库、无有效描述、资源/清单类仓库（awesome / dataset / benchmark / cheatsheet 等）、stars < 20。
  • 相关性双判定：项目自述（描述+名称）必须命中 AI/智能体语义词，且整体命中插件语义词或平台专属 topic。仅靠一个 topic 标签不足以入选 —— 否则通用工具会混进 AI 插件榜。匹配用词边界正则，避免子串假阳性。
  • 官方市场快速通道：来自第六节官方清单的条目，官方收录本身即强准入信号，不做 stars ≥ 20 门槛与 AI 语义词筛查（很多官方插件仓库自述根本不提 AI），但仍剔除已归档仓库、空描述与资源清单型仓库，并在榜单中标「官方」。
  • 新建仓库 < 14 天：分数 ×0.85 冷却；同一作者批量插件（>5 个）：×0.97 轻微降权；增量 > 均值 +3σ 时截断。所有修正都写进详情页「评分拆解」下方。

六、本地官方市场清单（发现源）

GitHub topic 搜索只能发现「打了标签的仓库」，会漏掉各平台市场里已正式收录、但没打 topic 的插件。为此流水线只读本机下列清单文件，把它们作为权威发现源（绝不修改用户配置）：

平台清单文件可得字段
Claude Code~/.claude/plugins/marketplaces/*/.claude-plugin/marketplace.json插件名、描述、作者、分类、版本 ref、source.url（多为 GitHub 仓库）、子目录路径
Codex~/.codex/plugins/cache/**/.codex-plugin/plugin.json名称、版本、描述、作者、homepage
WorkBuddyconnectors.json、各 marketplace.json、插件缓存、.skill-list-cache.json中英双语描述、类型、版本、可见范围、部分 repository
dshdsh --profile web --dump-config + profiles/*/package.jsonnpm 包名（可查周下载量）

三条口径必须分清：

  • 官方收录 ≠ 指标。清单只用于「这个插件确实存在、确实被官方收录」的发现与准入，stars / 下载量一律另经公开 API 复核；清单里没有任何数字会被当作评分输入。
  • 插件 ≠ 仓库。一个 marketplace 仓库常承载几十个插件（如 git-subdir 子目录）。总榜按 owner/repo 合并成一个实体，避免刷屏；详情页列出该仓库承载的全部官方插件名，目录页则按插件粒度展示。
  • 闭环留痕。本机清单每次运行会生成快照提交到 data/marketplace-sources/，GitHub Actions 云端跑不到用户目录时改读快照，口径与本机一致。查不到公开指标的条目标 n/a 并列入运行报告，不猜、不补。

七、数据源与证据链

只使用 api.github.com/search/repositories、api.github.com/repos/* 与 api.npmjs.org/downloads 的公开返回。第三方榜单的 stars / 安装量一概不采信，最多作为发现线索，进榜前必须自行调用 API 复核。

官方清单里指向的仓库先用 Search API 的多个 repo:owner/name 限定符批量取（走 search 独立配额）；实测有一批真实仓库不在搜索索引中（返回 422「资源不可搜索」，例如 anthropics/claude-plugins-public），这些再用 GET /repos/{owner}/{repo} 二次复核，REST 仍 404 才判为不可核验。所有结果含「确认查不到」都写入 data/repo-metadata.json 缓存，7 天内复用，既不臆造也不每天重查死链。

每条记录保存采集 query、UTC 采集时间、API 端点与当时的原始字段，详情页「证据链」表格可直接对照回查。每日运行报告在 state/run-YYYY-MM-DD.json，含全部淘汰条目与理由。

八、跨日比较请注意

分数是当日相对分位，样本集与有效权重每天都可能变化，因此分数绝对值不可跨日比较。跨日只看排名与排名变化（▲/▼），详情页趋势曲线展示的是同一口径下的历史采样，供参考而非精确审计。

九、怎么自己复算

GITHUB_TOKEN=xxx python pipelines/run_daily.py
python pipelines/run_daily.py --dry-run # 只算不生成榜单产物
python pipelines/run_daily.py --no-local-market # 只跑 GitHub topic 采集（对照用）
python pipelines/run_daily.py --no-market-npm # 跳过 dsh 包名下载量查询

权重、query、准入词表在 pipelines/config.py，评分在 pipelines/score.py，官方清单解析与仓库核验在 pipelines/local_market.py。当日生效权重写进 data/top100.json 的 meta.scoring；官方目录在 data/marketplace.json；仓库/npm 元数据缓存在 data/repo-metadata.json 与 data/npm-metadata.json。改口径请同步改这一页的说明。

没有 GITHUB_TOKEN 时，GitHub 未认证限额为 Search 10 次/分钟、core 60 次/小时。首次运行需批量核验约 240 个仓库（约 3 分钟），之后靠缓存几乎零请求。建议设置 token，可显著提高限额并缩短首次运行时间。
